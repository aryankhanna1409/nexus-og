## What Aegis-Net is

Imagine you run a city's bus network. One morning passengers complain that buses are late on four routes. A dispatcher looks at a map, a spreadsheet of delays, and a list of changes made overnight: a new software release for the ticket machines, a road closure, a staff roster change. Finding which change caused the delays means gathering evidence from several places, ordering events in time, and ruling out suspects. Then someone has to decide what to do, and the decision should be recorded.

Aegis-Net does the same job for a mobile telecommunications network, in software. It is a prototype that:

- reads call-detail records (CDRs) with a C library and computes call statistics and outliers;
- watches network key performance indicators (KPIs) such as latency and packet loss for anomalies;
- correlates anomalies with deployments, configuration changes and security events into an incident;
- runs an AI-assisted root-cause analysis (RCA) that can only use read-only tools;
- writes an incident report; and
- runs a policy-gated DevSecOps agent that proposes fixes, waits for human approval where required, verifies the result, and records everything in a tamper-evident audit log.

> [!WARNING] All data in Aegis-Net is synthetic. The telemetry, call logs, deployments, security events and DEMO-CVE advisories are generated by this repository. No real network, customer or vulnerability is described, and the production rollback is a simulation. [[S]]

## The problem it addresses

Network operators run thousands of cells (radio sites) served by gateways and core software. When service degrades, three things make investigation slow:

1. **Evidence is scattered.** Metrics live in a monitoring system, deployment records in a CI/CD tool, security alerts in an intrusion detection system (IDS), and logs on servers.
2. **Symptoms arrive in a cascade.** A single fault shows up as a dozen alerts, not one. The first symptom is often not the one people notice.
3. **Decisions need an audit trail.** Rolling back a production release is risky and must be justified and approved.

Manual investigation typically means: confirm the problem, find the affected elements, build a timeline, list recent changes, compare symptom order with how the system should behave, form a hypothesis, test it, act, and verify recovery. Aegis-Net automates the evidence gathering, ordering and bookkeeping. It does not automate judgement: confidence is capped, every cause is labelled a hypothesis, and risky actions need a human.

# Foundations for a Beginner

> [!NOTE] This chapter explains background concepts in plain language. It is general background, not a description of Aegis-Net features, except where it says "in Aegis-Net".

## What a telecommunications network does

A mobile network connects phones to each other and to the internet. A phone talks by radio to a **cell** (a radio site, sometimes called a base station). Cells connect through a backhaul network to **gateway** software in the core network, which routes traffic onward. In Aegis-Net the synthetic topology has 12 cells (`CELL-101` to `CELL-112`) served by three packet-gateway nodes (`pgw-1` to `pgw-3`), four cells each. Nothing about this topology is real; it is chosen to make shared-node failures easy to see.

## Call-detail records (CDRs)

A **call-detail record** is one row describing one call attempt: when it happened, who called whom, which cell carried it, how long it lasted, how it ended, and some radio quality numbers. Aegis-Net uses eight columns:

```text
timestamp,caller,callee,cell_id,duration,status_code,signal_strength,packet_loss
2026-03-01T14:05:00Z,+15550001,+15550002,CELL-102,184,200,-82,1
```

Operators analyse millions of such rows. Counting how many calls dropped in each cell, and spotting a cell that is much worse than its neighbours, is a standard first diagnostic.

## KPIs, counters and the metrics Aegis-Net tracks

A **key performance indicator (KPI)** is a number summarising service quality over a short interval. Aegis-Net samples 17 KPIs per cell every minute (units from `backend/app/simulation/metrics.py`):

Table: The 17 simulated KPIs

| KPI | Unit | Bad direction | Plain meaning |
|---|---|---|---|
| latency_ms | ms | up | Round-trip delay. If you shout and hear the echo 22 ms later, latency is 22 ms |
| jitter_ms | ms | up | How much the delay varies from packet to packet |
| packet_loss_pct | % | up | Share of data packets that never arrive: 3 lost per 100 is 3 % |
| throughput_mbps | Mbit/s | down | Delivered data rate |
| retransmission_rate | % | up | Share of data sent again because it was lost |
| rssi_dbm, rsrp_dbm | dBm | down | Received signal strength (RSSI) and reference signal power (RSRP); closer to 0 is stronger, so -80 dBm is better than -110 dBm |
| rsrq_db, sinr_db | dB | down | Signal quality and signal to interference-plus-noise ratio (SINR) |
| handover_success_rate / failure_rate | % | down / up | Whether a phone moving between cells keeps its call |
| call_setup_success_rate | % | down | Share of call attempts that start |
| call_drop_rate | % | up | Share of established calls that end abnormally |
| cpu_utilization, memory_utilization | % | up | Load on the serving gateway: 57 % memory means 57 of every 100 units are in use |
| active_users | users | both | Connected users |
| bandwidth_utilization | % | up | Backhaul usage |

"Bad direction" matters: a rise in latency is bad, a fall in throughput is bad, and users can be unusual in either direction.

## Anomalies, incidents and root causes

An **anomaly** is a measurement that is unusual compared with what is normal for that series, such as memory at 100 % when it normally sits near 57 %. An **incident** is an operational event that needs attention, built from several related anomalies. **Root-cause analysis (RCA)** asks which underlying change explains the symptoms. A symptom (high latency) is not a cause (a software release that leaks memory, which raises CPU, which raises latency).

## APIs, databases, containers, deployments

- An **application programming interface (API)** is how programs talk to each other. Aegis-Net exposes an HTTP REST API.
- A **database** stores structured records durably. Aegis-Net uses PostgreSQL in Docker and SQLite for the offline demo.
- A **container** packages software with its dependencies so it runs the same everywhere. **Docker Compose** starts several containers together.
- A **deployment** is a new software version going live on a server. Deployments are a prime suspect in incidents because they are deliberate changes.

## What an LLM does, and what an agent adds

A **large language model (LLM)** predicts text. Given a question and descriptions of available tools, it can answer with a request such as "call get_anomalies with these arguments". It cannot, by itself, do anything; a program must run the tool and give the result back. An **agent** is a program that wraps repeated cycles of observe, decide, act. In Aegis-Net the LLM only helps the RCA step (and writes one summary paragraph in reports). The DevSecOps agent's plan is deterministic and rule-based, which is a deliberate safety choice (Chapter 15).

> [!EXAMPLE] A worked mini-example. Suppose a cell's latency has hovered around 22 ms with a standard deviation of 1 ms. A reading of 250 ms is 228 standard deviations away. No judgement is needed to call that unusual. A reading of 24 ms is two standard deviations away and could easily be noise. Chapter 8 turns this intuition into algorithms.

## Why more than one language

- **C** for the hot, untrusted-input path: CSV parsing, grouped aggregation, robust statistics. Memory is managed explicitly, which is both the risk and the reason it needs sanitizer and fault-injection testing (Chapter 5).
- **Python** for orchestration, analytics, the API and the agent. NumPy handles series maths; SQLAlchemy and FastAPI handle persistence and HTTP.
- **TypeScript** for the dashboard so the API's JSON shapes are checked at compile time.
- **SQL** (via PostgreSQL) for relational integrity.

The languages meet at three explicit interfaces: the C header (`call_analyzer.h`), the REST API with its OpenAPI schema, and the database schema. CLAUDE.md requires such interfaces to be kept explicit.

## Trust boundaries

Four boundaries drive the security design: CSV into the C parser (untrusted, bounded); LLM output into the RCA engine and agent (untrusted, schema-validated); HTTP clients into the API (authenticated, authorised, rate-limited, size-limited); and the agent into the operating system (fixed executables, argument lists, confined directory, scrubbed environment).

# The C Call-Analysis Library

> [!STATUS] [[V]] Built with `-Wall -Wextra -Wpedantic` plus 13 further warning flags and `-Werror` (`c-library/CMakeLists.txt`). `make c-test` and `make c-test-asan` were run for this handbook: both reported "100% tests passed, 0 tests failed out of 2" (a normal and an allocation-failure-injection executable). The same test source holds 28 test functions.

## Public API and header design

The header `c-library/include/call_analyzer.h` is the authoritative contract. Its conventions are worth stating because every other layer relies on them:

- Functions returning `int` return `CA_OK` (0) or a negative `CaStatus`: `CA_ERR_NULL_ARG` (-1), `CA_ERR_INVALID_ARG` (-2), `CA_ERR_IO` (-3), `CA_ERR_NOMEM` (-4), `CA_ERR_PARSE` (-5), `CA_ERR_OVERFLOW` (-6), `CA_ERR_LIMIT` (-7).
- Arrays returned through out-parameters are allocated by the library and released only with the matching `free_*` function. On failure the output pointer is set to NULL and the count to 0.
- Fixed-size string fields (`char[32]`) are always NUL-terminated; inputs that do not fit are rejected, never truncated.
- There is no global mutable state in the production build, so calls are re-entrant.
- Only the public API is exported: the shared library is built with hidden visibility and `CA_API` marks the exported functions.

The main entry points are `parse_call_log_ex`, `parse_call_log_buffer`, `calculate_statistics`, `calculate_cell_statistics`, `calculate_failure_code_statistics`, `calculate_time_window_statistics`, `calculate_caller_statistics` and `detect_call_anomalies`.

## Structures

`CallRecord` holds four 32-byte strings, four `int` fields (duration, status code, signal strength, packet loss) and an `int64_t epoch_seconds`. Statistics structures (`CallStatistics`, `CellStatistics`, `TimeWindowStatistics`, `CallerStatistics`, `FailureCodeStatistics`) hold counts as `size_t` and rates as `double`. `CaStructSizes` exports `sizeof` of every structure so the Python binding can verify its mirrors at load time (Chapter 6).

## Parsing, validation, strict and lenient modes

The parser (`src/parser.c`) reads line by line, either from a file or from a memory buffer, and is deliberately strict about what it accepts.

- **Header detection.** If the first non-blank row's first field equals `timestamp` (case-insensitive), the row is treated as a header and all eight column names must match in order; otherwise the file is headerless. A UTF-8 byte-order mark on line 1 is skipped.
- **Quoting.** A hand-written splitter (`split_csv`) supports quoted fields with doubled quotes, rejects a stray quote inside an unquoted field, and rejects text after a closing quote.
- **Limits.** Lines longer than 1024 bytes, fields longer than the internal maximum, embedded NUL bytes and more than eight fields are rejected.
- **Validation.** Timestamps are ISO-8601 UTC; caller and callee are 1 to 31 characters from a restricted set; duration is 0 to 86,400 s; status code 100 to 999; signal strength -150 to 0 dBm; packet loss 0 to 100 %.
- **Strict versus lenient.** With `ParseOptions.strict` non-zero the first invalid row fails the whole parse; otherwise invalid rows are counted and skipped.
- **Parse report.** `ParseReport` records lines read, records parsed, records rejected, whether a header was present, and the line number, status and message of the first error. On failure `records_parsed` is reset to 0.

The default limit is 10,000,000 records (`CA_DEFAULT_MAX_RECORDS`); exceeding it returns `CA_ERR_LIMIT`.

## Status-code classification and rate formulas

> [!WARNING] The ranges and formulas below are Aegis-Net's own conventions. They are SIP-inspired but are not a universal telecom standard, and real networks use many other cause-code schemes.

Table: Status-code classes (`call_outcome_for_status` in `src/utils.c`)

| Range | Class | Meaning in this project |
|---|---|---|
| 200 to 299 | `CALL_COMPLETED` | Completed normally |
| 900 to 999 | `CALL_DROPPED` | Established, then ended abnormally (for example 901 radio link failure) |
| 300 to 899 | `CALL_SETUP_FAILED` | Never established (for example 408 timeout, 486 busy, 503 unavailable) |
| 100 to 199 | `CALL_UNKNOWN` | Provisional; counts as neither success nor failure |

$$ success_rate = completed / total $$
$$ drop_rate = dropped / (completed + dropped) $$
$$ setup_failure_rate = setup_failed / total $$

Drops are measured against *established* calls, the conventional definition. Example: 100 calls, of which 90 complete, 6 fail setup, 3 drop and 1 is provisional. Then success_rate = 90/100 = 0.90, drop_rate = 3/(90+3) = 0.0323, setup_failure_rate = 6/100 = 0.06. The code is short enough to read in full:

```c
CallOutcome call_outcome_for_status(int status_code)
{
    if (status_code >= 200 && status_code <= 299) {
        return CALL_COMPLETED;
    }
    if (status_code >= 900 && status_code <= 999) {
        return CALL_DROPPED;
    }
    if (status_code >= 300 && status_code <= 899) {
        return CALL_SETUP_FAILED;
    }
    return CALL_UNKNOWN;
}
```

Note the order: the dropped range is tested before the wide 300 to 899 range only for readability; the ranges do not overlap.

## Aggregations

Statistics are computed with running accumulators (`CaAccumulator` in `ca_internal.h`) that keep integer sums with overflow checks (`ca_accumulator_add` returns `CA_ERR_OVERFLOW` rather than wrapping) and a Welford running mean and second moment for duration spread. Cell statistics sort pointers to records by cell id; time windows align to multiples of the window size; caller statistics count distinct callees; failure-code statistics are sorted by count descending then code ascending. Results are sorted deterministically so tests and reports are stable.

## Call anomaly detection

`src/anomaly.c` compares each group with its peers using a *robust z-score*:

$$ z = (x - median) / max(1.4826 x MAD, floor) $$

where MAD is the median absolute deviation, the constant 1.4826 makes MAD comparable to a standard deviation for normally distributed data, and `floor` prevents tiny, tightly clustered baselines from inflating z. The score is

$$ score = 1 - 2^(-z / threshold) $$

so a group exactly at the threshold scores 0.5 (`ca_anomaly_score`). Severity bands are score at least 0.9 critical, at least 0.75 high, at least 0.6 medium, otherwise low (`ca_severity_for_score`).

> [!NOTE] External background (consulted): the NIST/SEMATECH e-Handbook defines a modified z-score as 0.6745 times the deviation from the median divided by MAD, and suggests flagging absolute values above 3.5 as potential outliers [R4]. 0.6745 is the reciprocal of 1.4826, and the library's default group threshold is also 3.5. Aegis-Net adds floors and minimum absolute deltas on top; it does not claim to implement the handbook procedure unchanged.

The defaults (`anomaly_config_default`): group z threshold 3.5, per-call duration threshold 10.0, at least 3 peer groups, at least 20 calls per cell, 10 per window, 20 per caller, 30 established calls for duration outliers, 300-second windows, minimum absolute deltas of 5 percentage points for rates, 6 dBm for signal, 3 points for packet loss, volume ratio 2.0, short-call ratio 0.6, and at most 1000 anomalies kept. A group is flagged only when *both* z reaches the threshold *and* the absolute deviation reaches the minimum delta. Anomaly types: cell drop rate, cell setup-failure rate, cell low signal, cell packet loss, window drop rate, window volume spike, caller high volume, and call duration.

The cell detector shows the pattern:

```c
for (size_t k = 0; k < n; k++) {
    const CellStatistics *c = &cells[idx[k]];
    CallAnomaly a;
    if (z[k] < cfg->z_threshold ||
        (double)directions[m] * (values[k] - median) < deltas[m]) {
        continue;
    }
    init_anomaly(&a, types[m], c->cell_id, values[k], median, z[k], cfg->z_threshold,
                 cell_sample(c, (CellMetric)m));
    ...
}
```

`directions[m]` is +1 when a higher value is worse (drop rate) and -1 when lower is worse (signal), so one comparison handles both. In the seeded run the library flagged setup-failure and packet-loss anomalies on exactly CELL-101 to CELL-104, for example "Cell CELL-103 setup failure rate 14.2% vs peer median 0.8% (1419 calls)" (Figure {@fig-callshot}).

## Memory allocation and ownership

All allocation goes through wrappers (`ca_malloc`, `ca_calloc`, `ca_realloc_array`, `ca_free`). `ca_realloc_array` fails on multiplication overflow, which blocks the classic "count times size wraps around" bug. Under the build flag `CA_FAULT_INJECTION` the wrappers can be told to fail the *n*th allocation, which lets the test `test_oom_all_operations` force every allocation site to fail in turn and check that each returns `CA_ERR_NOMEM`, frees what it had and leaves outputs NULL. Multi-step functions use a single cleanup label (`goto done`) so every path releases its temporary buffers, as the cell detector above does.

Native memory ownership matters because a leak or double free in a long-running service is hard to see from Python, and because the Python process cannot be protected by garbage collection from native mistakes.

## ctypes from first principles

A **shared library** (`libcallanalyzer.so` on Linux) is compiled code that other programs load at run time. Python's `ctypes` module can load one and call its functions, but C functions carry no type information at run time, so Python must be told each function's signature. The official documentation describes `argtypes` (the C types a function expects, so ctypes can check and convert arguments) and `restype` (the return type, default `int`), and structures declared as a subclass of `Structure` with a `_fields_` list, laid out as the C compiler would [R1].

If a signature is wrong, nothing warns you: a 64-bit `size_t` passed as a 32-bit `int` silently truncates; a pointer returned as `int` is cut to 32 bits and crashes later. This is why Aegis-Net's binding is paranoid.

## Structure layout and the ABI

The **application binary interface (ABI)** is the machine-level contract: field order, sizes, alignment and padding. In `backend/call_analyzer/_native.py` each C struct has a Python mirror. For example:

```python
class CallRecord(ctypes.Structure):
    _fields_ = [
        ("timestamp", ctypes.c_char * CA_FIELD_LEN),
        ("caller", ctypes.c_char * CA_FIELD_LEN),
        ("callee", ctypes.c_char * CA_FIELD_LEN),
        ("cell_id", ctypes.c_char * CA_FIELD_LEN),
        ("duration", c_int),
        ("status_code", c_int),
        ("signal_strength", c_int),
        ("packet_loss", c_int),
        ("epoch_seconds", c_int64),
    ]
```

Four 32-byte arrays occupy 128 bytes; four 4-byte ints bring the offset to 144, already a multiple of 8, so the 8-byte `epoch_seconds` needs no padding and the struct is 152 bytes. The binding does not assume this arithmetic. At load it calls `call_analyzer_struct_sizes` and compares every entry with `ctypes.sizeof` of the mirror; any mismatch raises `LibraryLoadError`. It also requires major version 1. The tests go further: they compile a C probe using `offsetof`, `sizeof` and `_Generic` against the header and compare each field's name, order, offset, size and type class with the Python mirror.

## Function prototypes and pointers

`_PROTOTYPES` lists `(restype, argtypes)` for every function used, for example `calculate_cell_statistics` takes a `POINTER(CallRecord)`, a `size_t`, a pointer to a `POINTER(CellStatistics)` and a pointer to a `size_t`. Out-parameters are created as `ctypes.POINTER(T)()` (a NULL pointer) and passed with `ctypes.byref`.

## Native allocation, freeing and exception mapping

Figure: C to Python call, ownership and release {id=fig-binding width=6.5}
![Figure](assets/diagrams/03_c_python_binding_memory.png)

{@fig-binding} shows the rule: the library allocates, Python copies results into dictionaries, and then frees with the matching `free_*`. The helper `_collect_array` does this in a `try/finally`, so the array is freed even if conversion raises, relying on the C guarantee that `out` is NULL on failure and `free(NULL)` is harmless. The outer `finally` in `analyze_call_log` calls `free_call_records` after all analyses. Result: no native pointer escapes.

Non-zero statuses become exceptions through `error_from_status`: a `CallAnalyzerError` base class carrying `code`, `code_name`, the library's own message and, for parse failures, the parse report, with subclasses such as `CallLogParseError`, `OutOfMemoryError`, `CallAnalyzerOverflowError` and `LimitExceededError`, plus `LibraryLoadError` for loading failures.

## Library discovery

`resolve_library_path` tries, in order: the `CALL_ANALYZER_LIB` environment variable (a non-blank value must point to a file or loading fails; there is no silent fallback), `c-library/build/libcallanalyzer.so` (from `make c-build`), then `/usr/local/lib/libcallanalyzer.so` (the Docker image). It always loads by absolute path, never through the dynamic linker search path.

## Why integer width and overflow validation matter

Before calling C, the binding rejects arguments ctypes would silently wrap: `window_seconds` outside the int64 range, a negative `max_records`, overrides that overflow a C `double` or `size_t`, NUL bytes in the path, and unknown `anomaly_config` keys. Python integers are unbounded; C integers are not. Without these checks, `window_seconds = 2**63` would become a negative number inside C.

## Why Python orchestrates and C computes

The binding module states the rule: *all computation happens in C*. Python converts structs, names enum values using the C `*_name` functions, and takes anomaly defaults from `anomaly_config_default`. The only Python-side derivation is `suspicious_time_windows`, which groups the window-category anomalies C returned and joins them to that window's C statistics, and it raises an error rather than invent a value if C returned a window with no statistics. Keeping computation in one place prevents two implementations from drifting apart.

# Synthetic Network Telemetry

> [!STATUS] [[S]] The simulator is a testing instrument. [[V]] Its determinism and causal properties are tested (`test_simulation.py`, 31 tests).

## What it produces

`simulate(Scenario)` returns, for 12 cells at one-minute resolution (default 360 minutes starting 2026-03-01T12:00Z): the 17 KPIs of Chapter 2, operational events (deployments, configuration changes, security events, application logs), deployment records and a ground-truth description used only by tests and the demo. Detection and RCA never read the ground truth.

## Baselines, load cycle, noise and determinism

- **Diurnal load.** `diurnal_factor` scales users by `1 + 0.25 sin(2 pi (hour - 12) / 24)`, so load peaks near 18:00 UTC and bottoms near 06:00.
- **Per-cell profile.** Each cell draws base users (160 to 260), base RSRP (-94 to -88 dBm) and base SINR (15 to 20 dB).
- **Noise.** Every metric carries autoregressive AR(1) noise with coefficient 0.7, so consecutive minutes are correlated rather than independent draws, as in real series.
- **Seeding.** NumPy `SeedSequence` spawns independent streams for profiles, incidents, background events and each cell, so identical scenarios give identical output. `SimulationResult.fingerprint()` is a SHA-256 over all values and events; the seeded scenario's fingerprint begins `aed745627289`.

## The causal model

Figure: The simulator's causal chain {id=fig-causal width=6.5}
![Figure](assets/diagrams/04_telemetry_causal_chain.png)

The terms in `model.py` implement {@fig-causal}. In brief: memory is `50 + 8 x load` plus any leak; CPU is `22 + 35 x load` plus garbage-collection pressure `1.8 x max(0, memory - 75)`; queueing delay is `4 u / (1 - u)` ms for utilisation `u = CPU/100`, capped at 400 ms, added to an 18 ms base for latency; packet loss adds a logistic overflow term that switches on near 93 % CPU. ## Worked example used throughout

Take ten one-minute readings of a KPI: 50, 51, 49, 50, 52, 50, 51, 49, 50, then 80.

Figure: The worked example, with baseline, threshold and EWMA {id=fig-example width=6.3}
![Figure](assets/charts/chart_detector_example.png)

## Moving average and rolling standard deviation

**Intuition.** What has this series typically looked like recently? **Definition.** Over a trailing time window W (60 minutes by default), the mean is the sum of values divided by their count, and the standard deviation is the square root of the average squared distance from the mean. **Example.** For the first nine readings the mean is 50.22 and the standard deviation 0.92. **Parameters.** `window_seconds = 3600`, `min_baseline_points = 20` before z-detection starts. **Implementation.** `_Baseline` keeps a deque of (time, value) pairs plus running sums, evicting old points by *time* rather than count so gaps and irregular sampling work. The helpers `moving_average` and `rolling_std` exist for charts and reports. **Strengths.** Simple, explainable. **Weaknesses.** A long window reacts slowly; a short one learns the anomaly. **Tests.** Detector unit tests on synthetic steps, ramps and gaps.

## Z-score

**Intuition.** How many "typical wobbles" away is this reading? **Definition.**

$$ z = (value - mean) / max(std, scale_floor) $$

oriented so that positive means the *bad* direction for that KPI. The floor is `max(noise_floor, relative_floor x |mean|)` per metric (`config.DEFAULT_RULES`), so a very quiet series cannot turn trivial changes into huge z. **Example.** Using latency's noise floor of 1.0: z = (80 - 50.22) / max(0.92, 1.0) = 29.8. **How it is used.** The z-score detector's score is `1 - 2^(-z/4)` (threshold 4.0), but only counts if the deviation also exceeds the metric's practical `min_delta` (6 ms for latency). **Strengths.** Standard and interpretable. **Weaknesses.** Assumes roughly bell-shaped noise; one big outlier inflates the standard deviation; ramps can drag the mean along, which is why the baseline admits only clearly normal points. **False positives.** Seasonal peaks the window has not seen. **Tests.** Step, ramp, spike and noise cases.

## EWMA

**Intuition.** A running average that forgets old data smoothly. **Definition.** `EWMA_t = alpha x Y_t + (1 - alpha) x EWMA_(t-1)`, the form given in the NIST handbook with smoothing constant between 0 and 1 [R2]. Aegis-Net makes alpha *time-aware*: `alpha = 1 - exp(-dt / tau)` with tau = 900 s, so a one-minute step gives alpha of about 0.0645. A matching exponentially weighted variance gives a standard deviation. **Example.** Starting at 50 with tiny wobbles the EWMA stays near 50.1; if the 80 were admitted it would jump only to 52.0 (the plain `ewma` helper output for this series, last point), showing how slowly an EWMA moves. **How it is used.** Its z is computed against the EWMA mean and variance; the detector flags only when z-score *and* EWMA agree (z at least 4 on both). **Strengths.** Cheap, adapts to slow drift. **Weaknesses.** Lags a sudden shift; the detector therefore never feeds flagged points into it. **Tests.** Time-awareness with irregular spacing.

## Absolute thresholds

**Intuition.** Some values are bad no matter what is normal. **Definition.** Per-KPI warning and critical levels, for example latency 100 ms and 200 ms, packet loss 2 % and 5 %, CPU 85 % and 95 %, memory 85 % and 95 %. A breach scores 0.7 (warning) or 0.95 (critical) and flags the point on its own. **Strengths.** Catches a series that has *always* been bad, and shows operators familiar numbers. **Weaknesses.** Fixed numbers encode judgement made for the simulator. **False positives.** A genuine, intended load increase.

## Rate of change

**Intuition.** Is the series moving much faster than it usually moves? **Definition.** Per-minute change compared with the median and MAD of recent healthy changes: `z = (rate - median) / max(1.4826 x MAD, floor)`, threshold 5.0, requiring at least 20 healthy changes and the practical-deviation gate. **Strengths.** Catches onset quickly. **Weaknesses.** Noisy at high sampling rates; on its own it does not flag, it needs support from z-score or EWMA.

## Scoring, severity, episodes and baselines

{@fig-scorecurve} plots the score against z for the C library (threshold 3.5), the Python z-score and EWMA detectors (4.0) and rate of change (5.0). Worked values at threshold 4: z = 4 gives 0.5, z = 8 gives 0.75, z = 12 gives 0.875.

Figure: Score as a function of z, with severity bands {id=fig-scorecurve width=6.3}
![Figure](assets/charts/chart_score_curve.png)

- **Flag rule.** A point is flagged if a static threshold is breached, or z-score and EWMA both reach 0.5, or rate of change reaches 0.5 together with one of them.
- **Severity.** `severity_for_score`: score at least 0.9 critical, 0.75 high, 0.6 medium, else low.
- **Episodes.** Flagged points closer than 300 seconds join one episode; an episode needs at least two points, or a single point scoring at least 0.85. The anomaly carries onset time, the most extreme value, the baseline at onset, the highest score, the detectors that fired and `related_metrics` (same-cell episodes overlapping within 15 minutes).
- **Baseline freeze and re-baselining.** Only points with |z| below 2.5 update the baseline, so neither a slow ramp nor a good-direction excursion can contaminate it. After six hours without any admitted point the series is re-seeded from current values, so a permanent level shift is eventually accepted as the new normal. Until then a permanent shift keeps being reported.

![Figure](assets/screenshots/shot_04_src-image5.png)

{@fig-anomshot} lists, per cell, the onset time, metric, baseline, worst value, severity, score and which detectors fired. ## Detectors versus the simulator

The simulator *creates* anomalies by changing drivers; the detectors know nothing about drivers. `analytics` modules import only the KPI catalogue from the simulator, and a test enforces that. This separation is what makes it meaningful that the detectors found the leak.

## Strengths, failure modes and limits across all detectors

- All four are interpretable: each flag can be traced to numbers.
- Thresholds and floors are hand-set per metric; there is no learning.
- Slow drifts that stay under thresholds for hours can be absorbed by the baseline.
- Multivariate patterns (two KPIs jointly unusual) are not modelled; correlation handles that at the incident level.

> [!NOTE] Future work (not implemented): Isolation Forest, an ensemble of random trees that isolates unusual points quickly, and DBSCAN, a density-based clustering method that labels sparse points as noise, are optional in the specification and are not part of Aegis-Net [[N]]. They are mentioned only as candidates for Chapter 20.

# Correlation and Root-Cause Reasoning

> [!STATUS] [[V]] `backend/app/analytics/correlation.py` and `causal_graph.py`; 29 tests in `test_correlation.py`. The recorded healthy-data check found 0 incidents over 20 healthy days (a recorded result, not re-run here). The seeded outputs below were recomputed for this handbook.

## Why symptoms share a cause

Nine KPIs turned critical in the seeded run, but there was one fault. A deployment leaked memory; memory pressure forced garbage collection and raised CPU; CPU raised queueing delay (latency, jitter); congestion lost packets; lost packets caused retransmissions, dropped calls and lower throughput. An operator who sees nine alerts needs the engine to group them and say which came first and what changed just before.

## What the engine actually computes

Figure: Evidence in, ranked hypotheses out {id=fig-corr width=6.5}
![Figure](assets/diagrams/06_event_correlation_incident_formation.png)

`correlate()` works in five steps ({@fig-corr}).

1. **Clustering.** Anomaly episodes on one cell whose start lies within 15 minutes of the cluster's span form a cell cluster. Cell clusters on the *same* node merge if their onsets are within 15 minutes; clusters on different nodes never merge.
2. **Incident gate.** A cluster becomes an incident only with at least two distinct symptom metrics and at least one symptom of severity high or above. This is why coincidental noise does not open incidents.
3. **Candidate causes.** Each candidate gets

$$ score = 0.45 x temporal + 0.35 x mechanism + 0.20 x topology $$

where *temporal* is `exp(-lead / 30 min)` for an event up to two hours before onset (0.3 for an event within five minutes after onset, 0.5 for symptom-only causes); *mechanism* is half the share of the earliest symptoms (within two minutes of onset) that the cause is expected to produce first plus half the share of all symptoms the cause explains in the causal graph; and *topology* is 1.0 when the event targets an affected node or cell and 0.5 otherwise. Event-backed classes are deployment regression, configuration change and security attack (needs at least 10 IDS events); symptom-only classes are memory exhaustion, traffic overload, radio degradation and transport fault.
4. **Exclusion.** Deployments and changes on other elements are listed in `excluded_candidates` with a reason.
5. **Confidence** `= top score x (0.6 + 0.4 x chain consistency)`, multiplied by 0.9 if the top two scores are within 0.1, capped at 0.95. *Chain consistency* is the share of effects that are preceded (within a one-minute tolerance) by at least one observed upstream cause in the fixed causal graph (`causal_graph.EDGES`).

> [!WARNING] Time ordering plus a hand-written graph is evidence, not proof. Statistical correlation does not establish causation, and the engine says so: every suspected cause has `status: "hypothesis"`, the incident carries a caveat to that effect, and confidence is capped.

The engine also records, for each adjacent pair of symptoms, the onset lag and (when series are available) the best lag of the Pearson correlation of first differences. In the seeded run that lag came out as 0 for most pairs (cross-correlation values from 0.44 to 1.0), so the *onset ordering*, not the cross-correlation lag, carries the temporal story. The report labels the sequence as temporal, not causal.

## Relational modelling in this project

Timestamps are stored as UTC epoch seconds in `BigInteger` columns so SQLite and PostgreSQL behave identically. # Authentication, Security, and Auditability

> [!STATUS] [[V]] `backend/app/security/`, `api/deps.py`, `agents/`; `test_security.py` (22 tests, 21 run; the live-Redis test is skipped without `AEGIS_TEST_REDIS_URL`), `test_api_core.py`, `test_agent.py`.

## Authentication versus authorisation

*Authentication* asks who you are; *authorisation* asks what you may do. Aegis-Net authenticates with bearer tokens: configured only as SHA-256 hashes in `AEGIS_API_TOKENS` (format `name:role:sha256`), compared in constant time against every entry (no early exit) with `hmac.compare_digest`. Raw tokens are generated by `make env`, written to the git-ignored `.aegis-tokens` file with mode 600, and shown only there. Tokens are accepted only in the `Authorization: Bearer` header, not in query strings, cookies or `Basic` auth (tested).

Authorisation uses four ordered roles, each including the lower ones: viewer (1), operator (2), approver (3), admin (4) (`config.Role` is an `IntEnum`).

| Verify the audit hash chain | no | no | no | yes |

## Approval gates

The policy (`agents/policy.py`) classifies each tool as READ_ONLY, LOW_RISK, REQUIRES_APPROVAL, HIGH_RISK or BLOCKED and returns allow, needs_approval or deny; Chapter 15 details the flow. The decisive point is that `execute_action` re-checks every rule immediately before running, so the API route is only a second line of defence.

> [!NOTE] A policy written in a document is only a promise. A policy enforced in application code, re-checked at the moment of action and covered by tests that try to bypass it, is a control. Aegis-Net's agent policy is the latter: the repository's tests include a test that an unapproved action cannot execute via the service and one that the initiator cannot approve their own action.

## Request identifiers, logging and audit

Every response carries `X-Request-ID` (a valid incoming value is echoed, otherwise generated); JSON access-log lines record method, route *template*, status, duration and actor. A log-record factory stamps `request_id`, `incident_id` and `agent_run_id` onto records. Tokens and API keys are never logged (tested).

The **audit log** is append-only. Each row stores `prev_hash` and `hash`, where the hash is the SHA-256 of a canonical JSON of the row's content plus the previous hash, starting from 64 zeros:

```python
def _digest(prev_hash: str, fields: dict[str, Any]) -> str:
    canonical = json.dumps({"prev": prev_hash, **fields}, sort_keys=True, separators=(",", ":"),
                           default=str)
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()
```

`verify_chain` walks the rows in order and reports the first row whose `prev_hash` or content hash does not match. Editing or deleting a row therefore invalidates every later link. The application code only ever inserts audit rows (the other uses of the table are reads for listing and verification), but the database itself has no trigger or permission blocking UPDATE or DELETE, so "append-only" is a property of the code plus the tamper evidence of the chain, not of the database. A caveat: a database administrator who recomputes all later hashes could forge a consistent chain, so for stronger guarantees the head hash would need external anchoring, which is not implemented [[N]].

{@fig-audit} shows rows for agent runs (`agent.run.start`, `agent.action.proposed`, `agent.action.succeeded`), a policy-engine block (`agent.action.blocked`, outcome denied), and a rejected self-approval by `local-admin` (`agent.action.self_approval_rejected`, denied). ## Input validation, limits and rate limiting

Pydantic `extra="forbid"` bodies; patterns on ids, metrics and cells; a 1 MB request limit enforced for declared and streamed bodies (413); security headers (`nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, a restrictive Content-Security-Policy on `/api/*`); and a fixed per-minute rate-limit window keyed by a hash prefix of the Authorization header or the client IP, using Redis when `REDIS_URL` is set and an in-process limiter otherwise (default 120 per minute; the Docker stack uses 600).

## Prompt injection and untrusted log content

Logs, security events and report text may contain attacker-controlled strings. Controls in the code: the RCA system prompt tells the model that tool results are data and any instructions inside them must be ignored; tools are read-only, incident-scoped and size-limited, so even a successful injection could only change what the model *says*, not what the system *does*; the model's answer must validate against a strict schema and cite real tool calls; and no LLM output ever becomes a shell command or tool choice in the agent. HTML reports are autoescaped and Markdown cells escape `|`, `\`, `<`, `>` and newlines (tested with injected `<script>` payloads), and the dashboard renders HTML reports in a sandboxed iframe.

> [!LIMITATION] A prompt in the system message is not a guarantee: a live model could still be misled into a wrong conclusion. The mitigation is structural (read-only tools, validation, human approval), not the prompt wording. Live-model behaviour against injected content was not tested [[U]].

## Safe command execution and secrets

Agent commands run only through `CommandRunner` (Chapter 15): fixed executables, `shell=False` enforced by an AST test, argument allowlists, a confined working directory, a scrubbed environment, a timeout and truncated output. Secrets are read from environment variables only; `Settings` marks keys and token hashes `repr=False`; `.env`, `.aegis-tokens` and virtual environments are git- and docker-ignored; no secret value appears in this handbook, the slides or the screenshots (checked).

# LLM Provider Abstraction

> [!STATUS] [[V]] interface, mock provider, provider selection, schema validation, and request-shape tests with fake SDK clients. [[U]] Anthropic, OpenAI and local providers were never called live: no API key was available, and the opt-in live test (`AEGIS_RUN_LIVE_LLM_TESTS=1`) was skipped in this session's run.

## Basics

An LLM receives a conversation and, when given *tool schemas* (JSON descriptions of functions with typed arguments), may reply with a request to call one. **Structured output** means the final answer must be a JSON object matching a schema. A **JSON schema** describes the allowed fields and types; **Pydantic** validates data against Python models and can export a JSON schema from them.

## Provider abstraction

`backend/app/llm/base.py` defines a provider-neutral interface: messages (`UserMessage`, `AssistantMessage` carrying the provider's raw content, `ToolResultsMessage`), `ToolSpec`, `ToolCall`, `ToolResult`, `LLMResponse`, and an `LLMProvider` with two methods: `generate(system, messages)` for plain text and `tool_call(system, messages, tools)` for one turn that may request tools. Providers translate to their wire format and *never execute tools*. Errors are normalised to `LLMRefusalError`, `LLMRateLimitError` and `LLMUnavailableError` (both retryable) and `LLMConfigurationError`. The abstraction matters because the RCA engine, reports and tests can then run unchanged against a deterministic mock offline and against a real model online.

Table: Providers as implemented

| `LLM_PROVIDER` | Class | Behaviour | Verification |
|---|---|---|---|
| `mock` (default) | `MockProvider` | Deterministic; delegates `tool_call` to a rule-based investigator and `generate` to a template; not an LLM | [[V]] used by tests, demo, screenshots |
| `anthropic` | `AnthropicProvider` | Official SDK, lazy import; default model `claude-opus-5-5`; effort set explicitly (`high`); every tool `strict`; tool choice auto; server-side refusal fallback beta; refusals checked first; assistant content echoed unchanged; SDK errors mapped | [[U]] request shape tested with fakes |
| `openai` | `OpenAIProvider` | Chat Completions with `strict` function tools; `MODEL_NAME` is required; malformed tool-call JSON surfaces as an invalid-arguments error | [[U]] |
| `local` | `OpenAIProvider(base_url=LOCAL_LLM_BASE_URL)` | Any OpenAI-compatible server | [[U]] |

Selection happens in `factory.build_provider`. If the chosen provider lacks its key, URL or SDK, the factory returns the mock and a `fallback_reason` that the API exposes; an unknown name also falls back. This keeps the system usable offline, but it means a misconfigured live provider silently becomes the mock unless someone reads the reason, so `/api/health` reports the provider name.

## Configuration

Environment variables (no values here): `LLM_PROVIDER`, `MODEL_NAME`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `LOCAL_LLM_BASE_URL`. Vendor SDKs are optional installs (`backend/requirements-llm.txt`; included in the Docker image).

{@fig-rcaseq} is the loop of `rca/engine.py`. The opening prompt contains only identifiers and symptom names, never raw data. # Root-Cause Analysis Engine

> [!STATUS] [[V]] with the mock provider; live providers [[U]].

## Workflow

1. **Incident selection.** `POST /api/incidents/{id}/investigate` (operator) loads the incident and moves it to `investigating`.
2. **Evidence collection** through nine read-only tools (`rca/tools.py`):

Table: RCA tools

| Tool | Returns |
|---|---|
| `get_call_statistics` | Overall statistics from the C analyser with per-cell figures |
| `get_cell_statistics` | Call statistics, call anomalies and metric anomalies for one cell |
| `get_metric_history` | One KPI on one cell, downsampled to at most 120 points |
| `get_anomalies` | Metric anomalies overlapping a time range |
| `get_related_events` | The incident's timeline, correlation hypotheses (answers only for the incident under investigation) |
| `get_recent_deployments` | Recent packet-gateway deployments |
| `get_security_events` | IDS events aggregated by category and target |
| `get_logs` | Log entries for one known service |
| `compare_baseline` | KPI mean in a range versus the preceding 60 minutes, per cell |

Tool limits: known metric names, cell patterns and services only; time spans of at most 24 hours; incident-scoped read-only database access; bounded output.

3. **Hypothesis generation and evaluation.** The answer must contain `facts`, `inferences`, `hypotheses` (cause type, confidence of at most 0.95, supporting and contradicting evidence, an assessment), `recommended_actions` (priority, risk class, optional agent tool) and `verification_steps`.
4. **Citations.** Facts and inferences cite tool-call ids. `validate_citations` rejects an answer that cites a call that did not happen, a fact with no *successful* call, or a leading hypothesis without supporting evidence from a successful call. The root cause must be the highest-confidence hypothesis and its confidence must match.
5. **Limits and retries.** At most 10 steps, 8 tool calls per step and 3 answer attempts; a rejected answer receives feedback; after the last attempt the RCA is stored as `failed` and no cause is invented.

## Facts, inferences, hypotheses, recommendations

Observed measurements are *facts* (each with a tool-call id). Relationships derived from facts are *inferences*. Candidate causes with confidences are *hypotheses*, and the headline is always labelled a hypothesis. *Recommendations* carry a risk class. The dashboard shows this explicit chain: observed evidence, correlated events, candidate hypotheses and evaluation, most likely root cause, confidence, recommended remediation.

## Presenting conclusions without exposing hidden reasoning

Provider "thinking" blocks are never stored or shown. What is stored is the structured facts, inferences, hypotheses, evidence references and recommendations plus the list of tool calls with arguments and results. # Report Generation

## Data model and numeric consistency

`ReportDocument` (`reporting/document.py`) is a Pydantic model with `extra="forbid"` and sections: KPI analysis, anomaly analysis, correlation analysis, root cause, impact, recommendations, verification steps, confidence, evidence references and timeline. `build_report` computes every figure from the database: for each KPI, the mean of the affected cells over the hour before onset (baseline) against the incident window, plus the worst value in the bad direction and the percentage change. Users connected is the sum over cells of mean `active_users`; call counts come from the C analysis and cover the whole analysed log for the affected cells (stated in the text, not just the incident window).

## Narrative and template fallback

Only the executive summary is generated prose. It comes from `LLMProvider.generate` (the mock uses a deterministic template) and is accepted only if every number in it appears in the JSON context the model was given (`_narrative_is_grounded`); otherwise the template is used and `narrative_provider` records the rejection. Provider errors also fall back to the template.

## Renderers and escaping

Jinja2 templates render Markdown and HTML from the same document. The HTML environment autoescapes, `StrictUndefined` makes a missing field an error, Markdown table cells escape special characters, and the HTML endpoint sends `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'` and `X-Content-Type-Options: nosniff`.

# Autonomous DevSecOps Agent

> [!STATUS] [[V]] `backend/app/agents/` with 36 tests in `test_agent.py`; the offline demo exercises the production-anomaly chain. [[S]] The rollback is a simulation. [[N]] `restart_service` has no model behind it and always fails with an explanation.

> [!WARNING] "Autonomous" is used in the project's name, but the planner is a deterministic set of rule-based playbooks. The LLM influences only the RCA text. It never chooses an agent tool, an argument or a command. Treat the agent as a *policy-controlled automation*, not as an LLM-driven decision maker.

## The loop

Figure: Agent lifecycle {id=fig-agent width=6.5}
![Figure](assets/diagrams/08_devsecops_agent_lifecycle.png)

A run moves OBSERVE, ANALYZE, PLAN, ACT, VERIFY, CLOSE and never backwards (`service._advance` raises if the planner attempts it). For each step the planner (`planner.next_action`) is a pure function of the run's action history: it names the tool, its arguments (built from earlier *results*, never from LLM text) and a rationale. `_propose` stores the action with that rationale *before* execution, evaluates the policy, and either executes immediately, parks it as `awaiting_approval`, or marks it `blocked`. A run stops advancing while any action awaits approval. A hard limit of 40 actions per run prevents loops.

## The sandbox and the disposable workspace

Code scenarios run in a throwaway copy of `demo-workspace/` (a small fictional packet-gateway service with tests) created under `AGENT_WORKSPACE_ROOT/<run>` with its own git history (`workspace.create_workspace`). `CommandRunner` (`agents/runner.py`) enforces:

- only two executables, `python` (this interpreter, `-m pytest` or `-m pyflakes`) and `git` (subcommands `init`, `add`, `commit`, `diff`, `log`, `apply`, `status`, `rev-parse`, `show`; no `-c` overrides);
- argument lists with `shell=False`, each argument checked for NUL bytes and length, a rule an AST test enforces over the codebase;
- the working directory must lie inside the workspace root, and workspace-relative paths are resolved and checked (`inside`);
- an environment scrubbed down to a fixed `PATH`, `HOME` set to the workspace, and git configuration disabled, so no inherited secret or `LD_PRELOAD` leaks in;
- a timeout (default 120 s) and output truncated at 20,000 characters.

A **container image** is an immutable bundle of a filesystem and start command; a **container** is a running instance. A **multi-stage build** has several `FROM` lines, and files are copied between stages so the final image carries only the finished output, not the compilers [R5]. **Docker Compose** declares several containers, their networks, volumes and start order in one file.

## The images

`backend/Dockerfile`: stage 1 (`python:3.12-slim` with gcc, libc headers, cmake, make) configures and builds `libcallanalyzer` in Release mode, **runs ctest during the build** (a failing C test fails the image build) and installs to a prefix. Stage 2 (`python:3.12-slim`) installs git (for the agent sandbox), creates the non-root user `aegis` (uid 10001), copies the library to `/usr/local/lib` and runs `ldconfig`, installs pinned requirements including the optional LLM SDKs, copies `backend/` and `demo-workspace/`, sets `AEGIS_DATA_DIR=/data`, and defines a health check that GETs `/api/health`. The entrypoint prints the library version, runs `alembic upgrade head`, optionally runs `python -m app.bootstrap` (loads the seeded incident into an empty database when `AEGIS_BOOTSTRAP_DEMO=true`; idempotent) and starts uvicorn on port 8000.

`frontend/Dockerfile`: a Node 22 stage runs `npm ci`, **Vitest and the build**, then nginx 1.27-alpine serves `dist`. `nginx.conf` proxies only `/api/` to `backend:8000`, falls back to `index.html` for client-side routes, answers `/healthz`, and sets security headers including a Content-Security-Policy. `/metrics` and `/docs` are not proxied.

## Troubleshooting

- *"run make env to create .env"*: the required variables are missing; run `make env` once.
- *Port already in use*: set `BACKEND_PORT` or `FRONTEND_PORT` in the environment.
- *Backend never becomes healthy*: `docker compose logs backend`; the entrypoint prints the library version first, then Alembic output. The smoke script prints the last 50 log lines in this case.
- *Agent reports odd test failures*: the plan records an earlier defect in which pytest was missing from the runtime image and the agent misdiagnosed; the image now installs the pinned requirements, so a rebuild (`docker compose build --no-cache backend`) is the first thing to try.
- *Dashboard shows login after a restart*: tokens live in `sessionStorage`; re-enter one from `.aegis-tokens`.
- *Provider shows `mock` although a key was set*: check `/api/health` and the backend log for the fallback reason.

# Limitations, Trade-offs, and Future Work

## Honest assessment

- **Synthetic versus real data.** All telemetry, incidents, CDRs, deployments and advisories are generated. Thresholds, floors and the false-positive bound were tuned on this simulator and generic synthetic series. Nothing here shows performance on real traffic.
- **Circular validation.** The simulator, the detectors' thresholds, the correlation graph and the tests share assumptions. The causal graph used for scoring mirrors the simulator's structure, so agreement is expected.
- **Unverified provider integrations.** Anthropic, OpenAI and local paths have never touched a live API; the mock is rule-based.
- **Optional algorithms not built.** Isolation Forest, DBSCAN; also no seasonal baseline, so a real daily cycle would raise false positives until the baseline learns it.
- **Deferred.** PDF reports; OpenTelemetry and Grafana.
- **Simulated rollback and narrow agent.** Patches are limited to reverting the last commit; `restart_service` is unmodelled.
- **Correlation limits.** Caller and per-call C anomalies are not turned into incidents; two independent faults on the same node with near-simultaneous onset would merge; correlation is not causation.
- **Performance unknown.** The pipeline runs synchronously in the request (a few seconds for 360 minutes of 12 cells). No load testing was performed.
- **Security gaps for production.** No TLS termination, no external identity provider or per-tenant RBAC, no secret manager, no high availability, `/metrics` is unauthenticated, the in-process rate limiter is per instance, and the audit chain is not externally anchored.

## Prioritised roadmap (recommendations, not existing features)

1. **Run a scored evaluation of live LLM RCA** against the same tools, with injected adversarial log lines. Rationale: the largest unverified claim.
2. **Replace the simulator's role in validation** by replaying a recorded, anonymised telemetry sample, and measure detector precision and recall.
3. **Move to asynchronous pipeline and agent runs** (a job queue) so requests return immediately.
4. **Add seasonal baselines** and a model-based detector beside the interpretable ones, keeping explanations.
5. **OIDC sign-in, TLS, secret manager, anchored audit head.**
6. **Patch generation beyond reverts**, validated in the sandbox, and real CI integration.
7. **OpenTelemetry traces** across API, RCA and agent.

# Advanced Technical Deep Dives

Each section says what is implemented and what is a production recommendation.

## C and Python ABI and memory ownership

*Implemented:* struct-size handshake, per-field `offsetof` tests, out-parameter ownership with matching `free_*`, `try/finally` release, overflow-checked arithmetic, argument range checks before crossing the boundary, allocation-failure injection. *Recommendation:* fuzz the CSV parser (for example libFuzzer) to reach inputs the unit tests do not; run the Python suite against the sanitizer build in CI (the Makefile target exists).

## Statistical detector design and trade-offs

The design chooses *interpretability and low false positives* over sensitivity. Requiring agreement of two detectors, a practical-deviation gate and baseline freezing trade some detection delay for a measured 0.27 false episodes per 100 series-days (recorded, synthetic). The cost is visible in the seeded run: memory is flagged at 14:13, eight minutes after the 14:05 deployment, which is consistent with the memory rule's practical deviation of 6 points while the leak grows about 0.8 points per minute. *Recommendation:* validate on real data before trusting any number.

## Evidence provenance and hypothesis evaluation

Every fact in an RCA carries a tool-call id; the validator refuses uncited or phantom citations; the persisted `tool_calls` hold arguments and results, so each statement can be traced to a database query. The correlation hypotheses carry a score decomposition (temporal, mechanism, topology), which {@fig-hyp} shows.

## Structured LLM tool execution

The engine is the policy enforcement point: the model proposes, the engine validates and runs. Two layers of schema validation, bounded steps, bounded results and read-only incident-scoped access limit what a misled model can do to the cost of a wrong answer, which the citation check and human review then catch or not.

## Policy enforcement and threat modelling

*Assets:* production deployments, repositories, the audit log, tokens. *Threats considered in code:* an LLM or attacker-influenced log steering actions (the agent ignores LLM text); a user approving their own action (blocked); an API caller bypassing the UI (policy re-checked in the service); a command escaping the sandbox (allowlist, `shell=False`, confinement); log or report injection into HTML (escaping, CSP, sandboxed iframe); brute force and flooding (rate limit, body limit). *Not covered:* a compromised host, a malicious database administrator, supply-chain attacks on dependencies (the project pins versions but does not verify signatures here).

## Database integrity

Foreign keys with cascades, unique audit hashes, run-scoped ids, one migration verified on two engines (recorded), and JSONB reserved for documents. An open design point is `agent_runs.incident_id`, a plain column without a foreign key, which the schema permits to dangle.

## Audit-chain verification

Verification is linear in the number of rows and needs only the stored columns. The dashboard's "Verify chain" requires admin. As noted, the scheme detects accidental or naive tampering but not a rewrite of the whole suffix.

## Integration testing

`test_e2e.py` runs the data-to-report chain and the agent chain through the real API; `test_offline_demo_runs_end_to_end` runs `scripts/demo.py`. These tests catch interface drift between layers that unit tests miss.

## Observability

*Implemented:* JSON logs with request, incident and agent-run ids; Prometheus metrics (`aegis_http_requests_total`, `aegis_http_request_duration_seconds`, `aegis_http_errors_total`, `aegis_rate_limited_total`, `aegis_agent_actions_total`, `aegis_rca_runs_total`) with bounded label cardinality (route templates). *Not implemented:* traces, dashboards, alerting.

## Performance and scaling considerations

Known: metrics are stored as one row per (cell, metric, minute) (12 x 17 x 360 = 73,440 rows per run), which is simple but will not scale to real fleets; the C parser is linear and the aggregations are `O(n log n)`. Unknown: throughput limits, memory under 10 million records, concurrent users. *Recommendations:* a time-series store, streaming ingestion and batch partitioning, but none of these is built.
